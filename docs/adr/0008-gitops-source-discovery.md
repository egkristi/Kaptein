# ADR-0008: GitOps source discovery and fallback

- **Status:** Accepted
- **Date:** 2026-08-21
- **Deciders:** Kaptein maintainers

## Context

The GitOps write path is the headline differentiator, but "locate the owning file/repo via
Flux/Argo metadata" was specified in one sentence. The hard problem: Flux puts
`kustomize.toolkit.fluxcd.io/name` and `/namespace` on a resource — which *Kustomization*
owns it, not which file. Argo gives `argocd.argoproj.io/tracking-id` — same problem. There
is no direct live-resource → source-file pointer.

## Decision

- **Owner discovery by re-render + match.** To find the owning file, re-render each
  candidate Kustomization/HelmRelease and match on GVK + name + namespace.
- **Cache the re-render results**, keyed by the source revision, so discovery is not
  re-rendered on every keystroke.
- **Explicit fallback when the source cannot be determined unambiguously:** resources
  generated by a Helm template, a Crossplane composition, a ConfigMap generator, or
  mutated by an admission webhook have **no single owning file**. In that case Kaptein
  does **not** open a PR; it shows *why* the source is ambiguous and what to edit instead.
  "We don't open a PR, we show why" is an acceptable and honest answer.

## Consequences

- **Positive:** the write path is honest about ambiguity instead of guessing; the
  differentiator survives contact with real GitOps layouts.
- **Negative:** re-render + match is expensive; the cache and its invalidation become a
  real subsystem (tracked under the GitOps milestone M2.3).

## Alternatives considered

- **Trust metadata alone** — rejected: metadata points at the reconciliation object, not
  the file; this would open PRs against the wrong file.
- **Require an explicit owner annotation** — rejected: breaks existing Flux/Argo installs
  and adds adoption friction.
